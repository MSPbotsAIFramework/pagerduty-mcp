## Product design

### Goals / Non-goals

**Goals** (v1, this ticket):
- An agent connected through the MSPbots Agent Platform can, against a tenant's own PagerDuty account:
  - list and inspect incidents, create (trigger) a new incident, and change an incident's state (acknowledge / resolve / escalate / reassign), and add a note to an incident's timeline;
  - list and inspect escalation policies (read-only — see non-goals);
  - list and inspect on-call schedules, and ask "who is on call" for a given policy/schedule and time window;
  - list, inspect, and open a post-incident review ("post-mortem") for an incident, including its action items.
- The connector follows the same request-header credential contract as every other MSPbots vendor MCP, so it plugs into the platform's existing "Credential form" connect flow with no platform-side UI change (Current state, above).
- Every tool call is isolated to the tenant whose credentials were sent on that request; nothing about one tenant's PagerDuty account is visible to, cached for, or reused by another tenant's calls (platform-wide requirement, SOP §3.3/§3.4).

**Non-goals** (explicitly out of scope for v1; each is a narrower read than "manage X" because the write side has either higher blast radius than a single ticket should authorize without being asked, or no concrete need was stated):
- **Creating, editing, or deleting escalation policies.** An escalation policy is an org-wide on-call structure shared by every incident that uses it; the ticket does not ask for a specific policy change, and getting this wrong silently misroutes every future page for every service on that policy. v1 exposes escalation policies read-only; escalating or reassigning a *specific* incident (a per-incident action) is in Goals.
- **Creating or editing on-call schedules, or schedule overrides** (e.g., "cover my shift tomorrow"). Same reasoning: a schedule mistake pages the wrong human for every incident it covers until someone notices. v1 exposes schedules and who-is-on-call read-only.
- **OAuth-based auth, or any auth mode beyond the single REST API key header.** PagerDuty's REST API v2 needs only an API key for everything this ticket asks for; no OAuth app registration is needed (unlike Acronis/Bloom Growth-style connectors in the wiki's "Connection forms" survey).
- **Webhook subscription management** (the gateway's generic per-connector "Webhook" dialog, seen in the wiki on Autotask). Not asked for; this connector registers no webhook-capable entities in v1.
- **The legacy PagerDuty "Postmortems" API/feature.** It is end-of-life in PagerDuty's own product the day after this design (2026-10-31); building against it would ship something already obsolete. "Post-mortems" in the ask is served by `/incident-reviews` (Decisions made by DEV01, Tech design).

### Acceptance criteria

- **AC1** — Given a request to any tool carries a valid `X-PagerDuty-Api-Key` header, when the tool calls PagerDuty, then the upstream request carries `Authorization: Token token=<that key>` and, if PagerDuty accepts it, the tool returns PagerDuty's data.
- **AC2** — Given a request to any tool is missing `X-PagerDuty-Api-Key` (or, for a write tool, missing `X-PagerDuty-From-Email`), when the tool is called, then the server responds `401` listing the missing header(s) by name — never a `500`, and no call is made to PagerDuty.
- **AC3** — Given incidents exist on the connected PagerDuty account, when `pagerduty_incidents_list` is called (optionally filtered by `statuses`, `service_ids`, `since`/`until`), then it returns the matching incidents with `items`/`count`/`limit`/`offset`/`has_more` (and `next_offset` when `has_more` is true), capped at PagerDuty's own page-size limit (100).
- **AC4** — Given an incident id that exists, when `pagerduty_incidents_get` is called, then it returns that incident's current fields (id, title, status, urgency, service, assignees, escalation policy, created/updated timestamps); when called with `include_notes=true`, the response also includes the incident's notes.
- **AC5** — Given a valid `service_id` and a title, when `pagerduty_incidents_create` is called, then PagerDuty triggers a new incident on that service and the tool returns the created incident (including the id PagerDuty assigned).
- **AC6** — Given an existing, open incident id, when `pagerduty_incidents_update` is called with `status="acknowledged"` (or `"resolved"`), then the incident's status changes accordingly in PagerDuty and the tool's response reflects the new status; given the incident is already in that status, the call is a no-op that still returns success (idempotent).
- **AC7** — Given an existing incident id and a target escalation level or a target assignee user id, when `pagerduty_incidents_update` is called with that target, then PagerDuty escalates or reassigns the incident accordingly and the tool's response reflects the new assignment/escalation level.
- **AC8** — Given an existing incident id and note text, when `pagerduty_incidents_add_note` is called, then the note appears on that incident's timeline in PagerDuty and the tool returns the created note (id, content, author, timestamp).
- **AC9** — Given escalation policies exist on the account, when `pagerduty_escalation_policies_list`/`_get` is called, then it returns the policy definition(s) including each escalation rule's targets and delay, with no write path exposed for this resource (Non-goals).
- **AC10** — Given on-call schedules exist, when `pagerduty_schedules_list`/`_get` is called, then it returns the schedule definition(s) (time zone, layers, rotation); when `pagerduty_oncalls_list` is called with a time window (defaulting to "now") and optionally a schedule or escalation policy id, then it returns who is on call in that window, with no write path exposed for either resource (Non-goals).
- **AC11** — Given a resolved incident, when `pagerduty_incident_reviews_create` is called for that incident, then PagerDuty opens a post-incident review for it and the tool returns the created review; when `pagerduty_incident_reviews_list`/`_get` is called, then it returns the review(s) (and, with `include_action_items=true`, their action items).
- **AC12** — Given PagerDuty returns an error (`404`, `429`, `5xx`, or a validation `400`), when any tool is called, then the tool returns the structured envelope `{"error": {"code": "...", "message": "...", "retryable": ...}}` with `code` from the fixed vocabulary (`not_configured`/`unauthorized`/`not_found`/`invalid_argument`/`rate_limited`/`upstream_error`) and PagerDuty's own error text folded into `message` — never an unhandled exception or a raw `500`; a `429` is reported with `retryable: true` and the tool does not retry past the single in-flight request's own backoff budget (Tech design §Non-functional).
- **AC13** — Given two concurrent requests carry two different tenants' `X-PagerDuty-Api-Key` values, when both call the same tool at the same time, then each request's outbound PagerDuty call uses only the key sent on that request — no response, cached token, or derived state leaks from one request into the other.
- **AC14** — Given this connector is registered on the platform (its `credential_fields` declared as `X-PagerDuty-Api-Key` and `X-PagerDuty-From-Email`), when an admin opens "Connect PagerDuty" from the platform's connector Library, then the standard credential form (ProductDocs/15-Capabilities.md § Connection forms, form 1) renders exactly those two fields and, once saved, the connector's detail view lists this service's tools (Current state) — no platform code change is needed for this to work.

## Tech design

### Conclusion

Build a new stateless Python 3.12 + FastMCP service in `MSPbotsAIFramework/pagerduty-mcp`, following the same shape as `halopsa-mcp`/`datto-rmm-mcp`/`connectwise-manage-mcp`: one `httpx`-based thin client against PagerDuty's REST API v2 (`https://api.pagerduty.com`), one credential middleware that reads `X-PagerDuty-Api-Key` (and, for write tools, `X-PagerDuty-From-Email`) per request via `contextvars`, and ~15 tools grouped by resource (incidents, escalation policies, schedules/on-calls, incident reviews). No new infrastructure, no new pattern — this is "another vendor of the same shape as the last three."

### Where the current implementation lives

Nothing — see Current state. This is SOP main line A (new service), built from scratch against `README.md:1-2` (the only existing content) and PagerDuty's own REST API v2 reference (`docs.pagerduty.com`, verified 2026-10-30).

### Option analysis

| Option | What | Pros | Cost | Verdict |
|---|---|---|---|---|
| A. Thin `httpx` client, hand-written, matching `halopsa-mcp`/`datto-rmm-mcp`/`connectwise-manage-mcp` | One small internal client module; error mapping, retry/backoff, and pagination handled in our own code per SOP §4/§5 | Identical shape to three other repos in this org — reviewers and future maintainers already know it; full control over the error envelope and retry policy the SOP requires; zero extra dependency surface or licensing to check | Hand-write pagination/retry (small — SOP already specifies the exact retry/backoff numbers) | **Chosen** |
| B. PagerDuty's official Python client library | Vendor-maintained request/pagination handling | Less code to write | Brings its own session/retry/auth model that would have to be bent to fit SOP §3.3's per-request, no-module-singleton credential rule (the library is designed to hold one long-lived API key per process, which is exactly the shape this platform forbids — one process serves many tenants); adds a dependency whose internals we do not control for the error-envelope and retry-budget requirements | Rejected — fighting a stateful SDK to make it stateless costs more than writing ~150 lines of client code |
| C. Generic HTTP passthrough tool (one tool, raw method+path+body) | Minimal code | Fast to build | Violates SOP §2's "tools are capabilities, not API-endpoint mirrors"; an agent would need to already know PagerDuty's REST API shape, defeating the point of an MCP tool layer; no `readOnlyHint`/`destructiveHint` semantics possible | Rejected |

No reason to deviate from the pattern this org has already used three times.

### Data & API contract

**Credential headers** (declared to the platform at publish time as this connector's `credential_fields`):

| Header | Required | Meaning |
|---|---|---|
| `X-PagerDuty-Api-Key` | Yes, every call | PagerDuty REST API v2 key (Account API key; created in PagerDuty under **Integrations → API Access Keys**). Sent upstream as `Authorization: Token token=<key>`. |
| `X-PagerDuty-From-Email` | Yes, write calls only (`pagerduty_incidents_create/update/add_note`, `pagerduty_incident_reviews_create`) | Email of a PagerDuty user on the connected account, sent upstream as the `From` header PagerDuty requires on every write (`docs.pagerduty.com`: incident updates "require a valid user email submitted with the `From` header"). Read-only tools do not require it. |

**Representative tool contracts** (full set in `README.md`'s tool table once implemented; shapes below fix the pattern every tool follows):

```
pagerduty_incidents_list(statuses?: string[], service_ids?: string[], since?: string, until?: string,
                          limit?: int ≤100 (default 50), offset?: int) -> str (JSON)
  -> {"items": [{"id","title","status","urgency","service":{"id","summary"},
                 "escalation_policy":{"id","summary"},"assignees":[{"id","summary"}],
                 "created_at","last_status_change_at"}, ...],
      "count", "limit", "offset", "has_more", "next_offset"?}

pagerduty_incidents_update(incident_id: string, status?: "acknowledged"|"resolved",
                            escalation_level?: int, assignee_user_ids?: string[]) -> str (JSON)
  -> upstream PUT /incidents/{id} {"incident": {"type":"incident_reference", "status"?: ...,
     "escalation_level"?: ..., "assignments"?: [{"assignee": {"id": ..., "type":"user_reference"}}]}}
  -> {"id","status","escalation_level"?,"assignees"[...]}  (the incident's new state, re-read)

pagerduty_oncalls_list(schedule_ids?: string[], escalation_policy_ids?: string[],
                        since?: string (default now), until?: string (default now)) -> str (JSON)
  -> {"items": [{"user":{"id","summary"},"schedule":{"id","summary"}?,
                 "escalation_policy":{"id","summary"},"escalation_level",
                 "start","end"}, ...], "count","limit","offset","has_more"}

pagerduty_incident_reviews_create(incident_id: string, summary?: string) -> str (JSON)
  -> upstream POST /incident-reviews {"incident_review": {"incident": {"id":..., "type":"incident_reference"},
     "summary"?: ...}}
  -> {"id","incident":{"id","summary"},"summary","status","created_at"}
```

**Error envelope** (every tool, on any failure):
```json
{"error": {"code": "not_found", "message": "PagerDuty: Incident PXXXXX not found", "retryable": false}}
```
`code` ∈ `not_configured` (missing/malformed header value), `unauthorized` (PagerDuty 401/403 on the key),
`not_found` (PagerDuty 404), `invalid_argument` (PagerDuty 400, or a locally-caught bad input before any
call is made), `rate_limited` (PagerDuty 429, `retryable: true`), `upstream_error` (PagerDuty 5xx or
network failure, `retryable: true`). Empty results are `{"items": [], "count": 0, ...}`, never `not_found`.

**No database, no migration**: this service is stateless end to end (SOP §1.3); PagerDuty is the only
system of record. **Backward compatibility**: not applicable — first version, nothing to be compatible with.

### Key flow / sequence

```
Agent (via MSPbots MCP gateway)
  -> POST /mcp  {tools/call: pagerduty_incidents_update, incident_id, status="acknowledged"}
     Headers: X-PagerDuty-Api-Key, X-PagerDuty-From-Email   (injected by the gateway per tenant)
  -> [credentials.py middleware] missing either header? -> 401, list what's missing, stop.
  -> [tools/incidents.py] validate incident_id is non-empty -> else invalid_argument, stop.
  -> [api.py client] PUT https://api.pagerduty.com/incidents/{id}
       Authorization: Token token=<api_key>
       From: <from_email>
       Accept: application/vnd.pagerduty+json;version=2
       Body: {"incident": {"type":"incident_reference","status":"acknowledged"}}
  -> PagerDuty: 200 (updated incident) | 404 (not_found) | 400 (invalid_argument)
             | 401/403 (unauthorized) | 429 (rate_limited, retry once after Retry-After, SOP §5)
             | 5xx (upstream_error, retry with backoff, SOP §5; budget < 120s total)
  -> [tools/incidents.py] map success -> {"id","status","escalation_level"?,"assignees"}
                            map failure -> {"error": {"code","message","retryable"}}
  -> Agent receives the tool result.
```

### Non-functional

- **Idempotency & concurrency**: no local state to race on (stateless, per-request `contextvars`, SOP §3.3). `pagerduty_incidents_update` to an already-matching status is a no-op success (AC6) because PagerDuty itself treats a repeated status transition as a no-op — not special-cased in our code.
- **Performance**: `/health` never calls PagerDuty (local-only probe, SOP §1.1). List tools cap at PagerDuty's own page ceiling (100) and our own response-size ceiling (≤ 20,000 chars, truncate + `has_more`/`next_offset` per SOP §2's token-economy rule). No n+1 calls: each tool issues exactly one upstream request per invocation (`pagerduty_oncalls_list`, `pagerduty_incidents_list`, etc. do not fan out per-item follow-up calls).
- **Security**: credentials read only from the two declared headers, never from env/config, never logged (SOP §3.1/§11); `gitleaks detect` run before delivery; no real credentials anywhere in the repo (SOP §11); `From`-email write-gating means a misconfigured tenant cannot silently write as an unidentified actor — a missing `From` is a 401, not a best-effort attempt.
- **Multi-tenant isolation**: `contextvars.ContextVar` set at request entry and `reset` in `finally` (SOP §3.3/§3.4) is the entire isolation mechanism — no module-level client, no cache keyed by tenant, no shared HTTP client session held across requests (a fresh client per request, SOP §5's "reuse the same HTTP client **within** a request", not across requests). AC13 tests this directly.
- **Observability**: structured log line per tool call (tool name, outcome `code` if any, latency) with no credential values or PagerDuty response bodies in the log — matches `halopsa-mcp`'s logging shape; no new log sink or alerting stood up for a first version (SOP's completion standard doesn't require one, and no ticket asked for one).

Single repo, single environment publish (no platform-side rollout — Non-goals/AC14 confirm no UI code changes). Sequence: merge to `main` → self-test on the merged code (SOP's completion standard) → `mcppub register` (new vendor, no existing INT registration to break) → INT health check + `tools/list` check. **Rollback**: this is a first version with nothing to roll back to; if the INT registration or health check fails, the review leg's `mcppub` flow reports `failed`/`rejected` and the ticket returns to `blocked` or a fix-forward round — there is no "previous working version" to revert to. No feature flag: the platform gates exposure per-tenant by whether that tenant has connected this connector at all (an unconnected tenant never sees it), which is the existing gating mechanism for every vendor connector, not something this ticket adds.

### Risks & dependencies

- **Risk**: PagerDuty's actual JSON field names/nesting for some resources (e.g., exact `incident-reviews` action-item shape) may differ in minor ways from what a schema reading predicts, since no live account is available to confirm against. **Mitigation**: fixtures are built from PagerDuty's published reference; any field-shape surprise found while implementing is a code-level fix, not a design-level one (the tool contracts above name the fields that matter to the AC, not an exhaustive passthrough of every PagerDuty field) — does not block merging or publishing to INT.
- **Risk**: this design's `/incident-reviews` mapping for "post-mortems" could be wrong if the requester actually meant the legacy feature or something account-tier-gated. **Mitigation**: recorded as a Decision (below) with the reasoning and the expiry date that forced the call; reversible in a follow-up ticket without touching anything else in this design if someone disagrees.
- **Dependency**: none on any other ticket or repo. Does not touch `mcp-service-gateway` or any control-plane repo (Track, below) — no gateway change needed, since credential injection and per-connector registration are existing gateway mechanisms this connector only needs to register into (`mcppub register`), not extend.

### Decisions made by DEV01

- **"Post-mortems" maps to PagerDuty's `/incident-reviews` API, not the legacy "Postmortems" feature.** Why: PagerDuty's Post-Incident Reviews REST API went GA on 2026-10-22 (8 days before this design); the older Postmortems feature is deprecated and scheduled for end-of-life in PagerDuty's web app on 2026-10-31 (the day after this design). Building a first version against a feature that expires the next day would ship something already obsolete. Alternative not chosen: building against the legacy `/postmortems`-style resource (if it still exists at all under REST API v2 — not confirmed, and not worth confirming given the EOL date).
- **Escalation policies and schedules are read-only in v1; only per-incident escalate/reassign is a write.** Why: both are org-wide, shared-blast-radius objects; the ticket names no specific policy or schedule change, so writing to them would be inventing scope under an authorization (automatic paging routes) rather than reading it off the ticket. Alternative not chosen: full CRUD on both, rejected as unauthorized scope expansion (Product design, Non-goals).
- **Nested sub-resources (incident notes, incident-review action items) are folded into their parent `get` tool via an `include_*` flag rather than given their own list tool.** Why: keeps the tool count at 14 (well under the 20 ceiling) and matches `halopsa-mcp`'s existing convention (`include_actions` on `halopsa_tickets_get`) rather than inventing a new shape. Alternative not chosen: a standalone `pagerduty_incidents_list_notes` tool — rejected, no behavioral difference, just more tools to read.
- **Credential is a single PagerDuty REST API v2 account key via `X-PagerDuty-Api-Key`, with a second required header `X-PagerDuty-From-Email` for write calls only.** Why: this is what PagerDuty's own API requires — there is no way to author a write without an identified human actor's email, and no OAuth path exists for REST API v2. Alternative not chosen: a single combined credential with no separate `From` concept — not possible, PagerDuty's API itself demands both.
- **No PagerDuty vendor SDK; hand-written `httpx` client matching the three existing single-token connectors in this org.** Why and alternative: see Tech design, Option analysis (Option B).
- **Snooze is not a v1 tool.** Why: not named in the ticket, and adding it later costs nothing (new tool, no existing contract changes). Alternative not chosen: including it preemptively — rejected per YAGNI; Open Questions records this as non-blocking.
